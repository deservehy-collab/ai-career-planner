# MySQL 求职档案改造：开发留痕

日期：2026-11-06
范围：六表结构、档案隔离、删除生命周期、前端档案上下文、旧数据显式迁移、回归与切换门槛。

## 阶段 1：六表底座与初始化

- 改了什么：新增 `backend/models.py`（`user_profiles`、`career_plans`、`analysis_rounds`、`tasks`、`growth_records`），`users` 留在 `backend/db.py`；`init_db` 幂等建表；默认 SQLite，`CAREER_DB_URL` 切 MySQL。
- 验证：`backend/tests/test_archive_db.py`（六表存在、幂等、级联删除、资料乐观版本）；`python -m backend.db --init` 在临时 MySQL 库建出六表。
- 风险：`python -m backend.db` 会把模块加载成 `__main__` 与 `backend.db` 两份，`Base.metadata` 不共享 —— 已改为统一从 `backend.models` 取元数据。
- 下一步：档案仓库与删除接口。

## 阶段 2：档案仓库、接口与删除

- 改了什么：`backend/plan_repository.py`（建档幂等、列表游标、行锁删除、计数摘要）、`backend/plans_api.py`（`/api/profile`、`/api/plans` 全套）、`backend/profile_service.py`（账号资料与快照）。
- 验证：`backend/tests/test_plan_api.py`、`test_plan_services.py`；越权与重复删除均 404；删除 A 后 A 的子表归零、B/账号/资料保留。
- 风险：同名岗位不同 JD 必须建两份；`request_key` 唯一约束兜住并发。
- 下一步：档案级 store 与运行生命周期。

## 阶段 3：档案级存储与运行生命周期

- 改了什么：`backend/plan_stores.py` 的 `SqlLoopStore` / `SqlGrowthStore` 从六表物化旧的 loop/growth 结构；`stores_for_plan` 校验归属；`jobs` 记录绑 `owner + plan_id`，删除后 `drop_plan`，迟到结果丢弃。
- 验证：`test_plan_stores.py`、`test_plan_services.py`（运行中删除、迟到回写、重试不重复）。
- 风险：模型推理期间不持事务；写入前重新确认档案仍存在（`PlanGone`）。
- 下一步：任务与成长全面限档。

## 阶段 4：任务与成长限档

- 改了什么：完成、待处理、撤回、作废、补录、清任务、下一轮全部只接收当前档案的 `Stores`；去掉跨档案汇总。
- 验证：`test_plan_services.py`、`test_growth_next_round.py`、`test_growth_loop_api.py`；A 的成长不出现在 B。
- 风险：旧账号级 JSON 兼容分支按“缺 plan_id 就取最新档案”会造成串档，接口已改为显式档案路径。

- 分析无法进行的根因（非代码缺陷，属配置）：`runs/settings.json` 的 `llm_channel=local`，但本机 Ollama 未启动（11434 连接被拒），首轮 ProfileAnalysis 直接失败。云端 `glm-4.7-flash` 已配置且实测可用：一次性进程切云端跑完整七步，Profile/Growth/Retrieval/Job/Assessment/Learning/Project 各 Agent 均完成（免费档限流会重试、偏慢）。解决办法二选一：系统状态页把通道切到云端，或先 `ollama serve` + `ollama pull qwen2.5:3b` 再用本机通道。未擅自改用户通道偏好。
- 数据位置：默认 SQLite 六表在 `runs/app.db`（账号/资料/档案/轮次/任务/成长）；旧账号级 JSON 仍在 `runs/users/user_<id>/`，只读不自动迁移；设 `CAREER_DB_URL` 可整体切 MySQL。
