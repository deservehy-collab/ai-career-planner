# 分析进度：从"整条轨在跑"到节点级真实状态

日期：2026-11-10
范围：`backend/jobs.py`、`backend/analyze.py`、分析页进度展示；不动业务数据、不改 `.env`。

## 阶段 1：后端把节点进度写进 run 记录

### 改了什么

- `TaskRecord` 新增 `progress` 与 `current_node`。每项进度：
  `{node, status, started_at, finished_at, duration_ms, error}`；
  `status` 取 `running | done | failed | skipped | canceled`。
- `TaskManager` 新增 `node_started / node_finished / node_skipped / node_interrupted`：
  - 任务异常退出时，把仍在 `running` 的节点记为 `failed`，错误与该次 run 同源；
  - 用户停止时，在跑节点记为 `canceled`，`current_node` 清空；
  - 正常返回却还有节点停在 `running`（执行体漏报结束）时如实记 `failed`，
    不冒充完成，也不让它永远显示"进行中"。
- `backend.jobs` 提供模块级 `report_node_*` 与 `inside_task_run()`：业务代码不拿 `run_id`，
  不在后台任务里调用是 no-op（CLI / 既有单测行为不变）。
- `backend/analyze.py` 新增 `_run_workflow`：
  - **在后台任务里**用 `workflow.stream(stream_mode=["debug", "values"])`，
    按 `debug` 的 `task` / `task_result` 事件逐节点回报，`values` 快照作为最终 state；
  - 节点抛异常时 LangGraph 不补 `task_result`，由 `report_node_interrupted` 把正在跑的
    节点记失败后再原样抛出；`task_result` 自带 error 同样让本次运行失败并定位到该节点；
  - 成功收尾时，本轮没走到的节点（assessment 之后走 END 的 learning/project）记 `skipped`；
  - **不在后台任务里**（CLI、既有直接调用测试）仍走一次性 `workflow.invoke`。

### 验证

- 新增 `backend/tests/test_node_progress.py` 共 10 条：生命周期可见、失败归因到节点、
  中断/取消关闭在跑节点、无上下文 no-op、流式逐节点回报、未走分支标 skipped、
  异常定位、`task_result` 错误、invoke 回退，以及 `GET /api/runs/{run_id}`
  原样带出 `progress` / `current_node`。
- 用真实 LangGraph（无模型）探针确认 `debug` 事件形状：`payload.name` 为节点名，
  `task_result.payload.error` 成功时为 `None`，条件分支本身不发 task 事件。
- `tests` + `backend/tests` 全量：**661 passed, 2 xfailed**（xfail 为既有项）。
- 原有取消测试的阻塞点从 `workflow.invoke` 改为 `workflow.stream`（后端已改走流式），
  测试意图不变：取消后不写轮次、不写成长、记录终态 failed。

### 风险

- `current_node` 是单值。将来 retrieval 与 profile/growth 并行后，会同时有多个
  `running` 节点，需要改成"当前步骤集合"的展示口径；数据结构本身（progress 列表）
  已经能容纳多个 running。
- 旧 run 记录没有 `progress`，前端必须退回"整条轨"的说法，不能编造节点状态。
- 「下一轮成长规划」仍走 `workflow.invoke`，本次只覆盖分析链路。

## 阶段 3：retrieval 与 profile/growth 并行

### 改了什么

- `graph/workflow.py` 拓扑：
  - `START` 同时扇出 `profile` 与 `retrieval`（依据整理不再排在能力画像后面）；
  - `profile → growth`；`growth → job` 与 `retrieval → job` 在 `job` 前汇合，
    `job` 看到的仍是"更新后的能力 + 完整岗位依据"；
  - `assessment` 之后的条件分支与 `learning → project → END` 保持不变；
  - `ORDER` 保留为展示/汇报顺序，不再等同于执行顺序。
- `utils/agents.js` 新增 `runningAgents(progress, currentNode)`：从后端 `progress`
  里取此刻 `running` 的节点（按展示顺序），旧记录没有 `running` 时才退回单值
  `current_node`。
- `AgentPipeline.vue` / `RunProgressCard.vue`：一个节点在跑时仍显示
  `正在执行「X」· 第 N/7 步`；两个节点并行时如实显示
  `正在并行执行「能力画像」「招聘要求整理」`，不把并行说成单节点顺序执行。
  后端 `current_node` 保持单值（兼容旧记录与查询接口），多节点信息以 `progress` 为准。

### 修掉的并行缺陷

- 降级提示原先用 `threading.local` 收集。LangGraph 的并行节点跑在线程池里
  （context 会随任务复制），分支里产生的提示在汇总时全部丢失。改为
  `ContextVar` 持有一个列表：各分支看到的是**同一个列表**，`take_warnings()`
  仍能收齐；追加用模块级锁避免重复。
- 实测确认：LangGraph 同步并行节点确实在不同线程执行，但 `_CURRENT_RUN`
  contextvar 会被复制过去，节点进度回报与取消判断在分支里仍然有效。

### 验证

- 新增 `backend/tests/test_workflow_topology.py` 3 条：START 双扇出、
  job 汇合两条分支、假节点互等证明 profile 与 retrieval **真的同时开始**。
- 新增 `backend/tests/test_llm_warning_parallel.py` 1 条：并行节点里的降级提示
  能被本次运行收走（修复前为空）。
- 后端全量：**666 passed, 2 xfailed**；前端 **19 个文件、124 passed**；
  `npm run build` 通过；后端已重启，`GET /api/ping` 200。

### 风险

- 两条分支会同时调用模型。本机 6GB 显存上 Ollama 可能排队或变慢；如果实测
  "并行反而更慢 / 显存不足"，应退回串行（只改回 `START → profile` 与
  `growth → retrieval` 两条边即可），不要靠加超时硬扛。
- 一条分支抛异常时整轮失败，另一条仍在跑的节点会连同记为失败（本次结果本来
  也不采用）；这是有意的诚实口径，不冒充完成。
- `current_node` 仍是单值，只用于兼容展示；并行状态一律以 `progress` 为准。

## 阶段 4：修复并行汇合导致的重复执行（用户截图反馈）

### 现象

分析进度卡出现「正在并行执行『学习路线』『实战项目』」与「已完成 8/7 步」。

### 根因

两条分支汇入 `job` 时用了**两个单独的 `add_edge`**：

```python
builder.add_edge("growth", "job")
builder.add_edge("retrieval", "job")
```

LangGraph 会**每条边各触发一次**：`job` 先带着不完整的上游状态跑一遍，再跑一遍；
`assessment / learning / project` 随之下游各跑两遍。于是进度里出现重复节点
（8 条 done）、两条执行线的 learning/project 交错成"并行"，还多花了模型调用。

### 修复

改为列表形式一次汇合，等两条分支都到齐再执行：

```python
builder.add_edge(["growth", "retrieval"], "job")
```

- 真节点探针验证：修复前 `job/assessment/learning/project` 各执行 2 次；
  修复后 7 个节点各执行 1 次，且 `job` 的输入同时含 `user_skills`、`skill_updates`
  与 `job_evidence`。
- 前端 `RunProgressCard` 的"已完成 N/7 步"改为**按节点去重并封顶**：
  旧记录/重跑导致重复 done 时也不会再显示 8/7。

### 验证

- 新增拓扑测试 1 条：每个节点只执行一次 + job 看到两条分支的产出（修复前失败）。
- 新增前端去重测试 1 条（修复前显示 8/7）。
- 后端全量：**667 passed, 2 xfailed**；前端 **19 个文件、125 passed**；构建通过。

### 风险

- 后端重启后，内存中的 run 记录会清空。截图时仍在跑的那次旧代码分析会被中断，
  需要重新发起一次；旧运行未保存任何结果。
