## 阶段 4 官方资料入库试点（内置资料摘要）

**做了什么**

- 新建 `agents/external_sources.py`：把仓库里人工整理的 `knowledge/jobs/*.yaml` 的 `skills[].evidence`
  转成 `job_evidence` 记录（形状与 `chunk_user_jd` 逐键对齐，实测过），带 `provenance = "official_digest"`、
  `company_slug = None`、原句照抄、出处 `source_id` 保留。
  护栏：每技能最多 2 条、全局最多 24 条、硬性要求优先于加分项、缺 source_id 或缺原句的直接丢。
- `agents/retrieval_agent.py` 三档降级：粘了原文 → 只用原文；没粘但岗位匹配到画像 → 用内置资料摘要；
  两者皆无 → `no_source` 空证据并写原因。`retrieval_status` 因此从两值变三值
  （`user_pasted` / `official_digest` / `no_source`）。
- 来源派生认 `provenance`，不认 `source_` 前缀：AI 岗位真实 source_id 是 `jd_hundsun_001` 这类，
  前缀规则会把内置摘要漏判成模型推断。`evidence_by_source` 进 `source_report`，前端分「你粘贴的原话 N 句」
  与「内置资料条目 N 条」两个数。
- **不越权**：摘要不能把 `requirement_basis` 从 `knowledge_base` 抬成 `user_pasted`；匹配度百分比由档位把关
  （前端 `hasSolidBasis()` 只认 `user_pasted`，`web/src/utils/enums.js:284`；档位判定在
  `agents/job_agent.py::resolve_requirements_basis()`）。`jd_match.py:170` 那句只挑「来源提示」文案，本轮未动。
  前端 `EvidencePanel` 按 provenance 分组，编号仍钉在数组下标（分组不重排 E 编号）。
- 知识库自检：`scripts/validate_knowledge.py` 新增 `[Sources]` 段与 evidence 缺字段即 SystemExit。
- `/status` 增「岗位资料」读数：4 个岗位、86 条可回查资料条目、9 份资料出处；`jobs.ok` 进入健康判定。

**发现的问题**
① 摘要条目里合法含有等级词（「熟练」「熟悉」），会派生出 `level_basis.origin = "jd_text"` —— 后端枚举不动，
改为把前端文案从「JD 原文」中性化成「依据原句」，避免把整理稿说成原话。
② `test_no_pasted_text_degrades_to_empty_evidence` 是**故意**被推翻的契约测试（原断言 `no_source`），
已换成两条新用例：已知岗位走摘要、陌生岗位仍 `no_source`。

**下一步**：阶段 5 全量回归 + 四情形浏览器对照 + 交付记录；golden 评测里 `eval_golden.py:92` 仍传
`enable_job_profile=False`，画像模式测不到，这条要如实写进已知问题。

**与原方案的偏离（决策 D3）**
方案里写的是新建 `knowledge/sources/*.yaml`，为 2 个岗位各手写 3 份匿名公开资料摘要。
实际做的是**复用 `knowledge/jobs/*.yaml` 里早已存在但断链的 `skills[].evidence`**（4 岗位、86 条、9 份 source_id），
用 `agents/external_sources.py` 转成 `job_evidence`。
理由：① 那 86 条本来就是人工整理、带出处的原句，再抄一份到 `knowledge/sources/` 只会造出第二个真相源；
② 零新增数据 = 零新增授权与匿名化风险，也不用手写内容；③ 试点要验的是「断链能不能接上、会不会越权抬高依据」，
换目录不改变这两件事的结论。
代价：这批资料的粒度是「按技能登记」而非「按岗位原文」，所以它天然只能当 `knowledge_base` 档的依据 ——
这正是 `requirement_basis` 不升档、匹配度不给出的原因，与产品立场一致。

**发现的问题**

① **文案把模型补的要求说成了有据**（实测情形 D：粘 3 句原文、7 条要求 0 条命中原话，
   旧文案仍写「这次的说法来自你粘贴的原文，所以照样能逐条回查」）。
   已改成按 `source_report.counts` 分两档说：0 条对上 → `warn` +「没有一条岗位要求能对上原话 ——
   下面 N 条都按模型推断对待，别当门槛」；对上若干条 → 「你粘的 X 句原文里，Y 条能直接对上原话，其余 Z 条是模型按常识补的」。
   用 D 的真实数字（3 句 / 0 条 / 7 条）补了单测。
   **改完用浏览器重跑 D 复验**：这次模型给出 2 条命中原话，界面变成「你粘的 3 句原文里，2 条岗位要求能直接
   对上原话，其余 8 条是模型按常识补的」（截图 `Temp/aicareer-e2e-1103/shots-d2/`）—— 顺带第二次证明
   同一条用例两次跑结果不同（0 条 vs 2 条），"0 命中"那一档只能靠单测锁，没法稳定复现。

② **`projects.min_from_kb` 挂了 8 条，两组对照实验证明不是本轮引入的**：
   - 实验 A：运行时把阶段 3 插入的 `gap_source_hint` 置空，重跑同样 8 条 →
     **7/8 仍挂在同一项**（只有 `acct-cost-project` 翻绿，属波动）。提示词那句"缺口来路"不是原因。
   - 实验 B：运行时把 `_digest_update` 关掉（没粘原文就退回改动前的 `no_source`），重跑同样 8 条 →
     **8/8 仍挂在 `projects.min_from_kb`**（内置摘要不是原因）。
   两条结论合起来：这 8 条与阶段 3、阶段 4 都无关，是本地 3B 没从项目知识库选出模板。
   结论口径：宁可写"两组实验排除了什么"，也不写"模型能力问题"这种无法核对的话。
   注意别拿通过率比大小 —— 两个实验都只盯 `projects.min_from_kb` 这一项，A 里翻绿的那条是波动。

③ **单次通过率不能当回归判据**：`acct-fresh-graduate` 在 10:37 那次跑 PASS、在 10:33 与本次全量跑 FAIL，
   同模型同参数。所以换 prompt/换模型之后要用 `--baseline` 看差集，不看绝对通过率。

④ **既有语义缺陷，本轮没动**：`agents/jd_match.py:160-165` 只要 `存在差距 > 0` 就给 `overall = "partial"`，
   实测情形 A 是「已满足 0 项、差距 3 项、满足率 0%」却显示「部分满足」。
   属于判定语义变更，会牵动目标达成与既有断言，不在本轮批准的四步内 —— 等人定。
