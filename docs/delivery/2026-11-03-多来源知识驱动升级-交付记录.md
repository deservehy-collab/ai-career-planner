## 2. 数据结构说明

### 2.1 四值来源口径（`agents/source_attribution.py`）

| 值 | 含义 | 判定依据 |
| --- | --- | --- |
| `user_jd` | 来自你粘贴的招聘原文 | 要求条目回查到 `provenance=user_pasted` 的证据句 |
| `official_data` | 来自内置岗位画像登记过的公开资料摘要 | 回查到 `provenance=official_digest` 的证据条目（带 `source_id`） |
| `knowledge_base` | 由内置岗位画像本身担保（等级/重要度取自人工画像） | `level_basis.origin` / `importance` 来自画像而非模型自述 |
| `model_inference` | 回查不到任何依据 | 兜底档 —— **包括模型自称引用了 `E88` 这类幻觉编号** |

唯一口径：**回查不到证据编号的一律算模型推断**。宁可少认一个来源，也不能把模型编的标成有出处。

### 2.2 `job_evidence` 条目（逐句记录，两种来路同形状）

```
{ skill, note(原句照抄), provenance: "user_pasted" | "official_digest",
  source_id, requirement_type: required|preferred|bonus, context, ... }
```
`provenance` 是新增值，不是新增键；旧数据没有该键时按「无出处」处理，不会被误认成原文。

### 2.3 `retrieval_status`（三值）与 `requirement_basis`（三档）

- `retrieval_status`：`user_pasted` / `official_digest` / `no_source` —— 描述**这一轮的证据从哪来**。
- `requirement_basis`：`user_pasted` / `knowledge_base` / `model_only` —— 描述**岗位要求能不能逐条对照**。
  匹配度百分比的开关就是它：前端 `hasSolidBasis()` 只认 `user_pasted`（`web/src/utils/enums.js:284`）。
  档位判定在 `agents/job_agent.py::resolve_requirements_basis()` —— 粘了原文但只要有任一条
  `evidence_status=model_supplement` 就不算全可靠；走内置画像一律 `knowledge_base`；两者皆无才 `model_only`。
  所以**摘要抬不动档位**。`agents/jd_match.py:170` 只挑「来源提示」那句措辞，本轮未动；
  `match_rate` 在「可判定数为 0」时返回 `null`（前端显示"无可判定要求"），不是 0%。

### 2.4 `source_report`（`build_source_report`，响应字段，不落盘）

`target_job` / `requirement_basis` / `counts`（四档计数，含 `total`）/ `citations`（与 `job_requirements` **逐条同序**）/
`model_only_skills` / `evidence_sentence_count` / `evidence_by_source`（原话句数与摘要条数分开的来源）/
`official_source_ids`（本轮真正用到的出处编号，排序去重）/ `catalog_profile_matched`（三值：`true`/`false`/`null`）/
`job_profile_origin`。

`catalog_profile_matched = null` 表示岗位目录本身读不出来 —— 前端此时**不许**说「这个岗位不在画像里」。

```

                   ├─▶ [1] Retrieval Agent
内置画像 evidence ─┘      三档降级：
   (knowledge/jobs/*.yaml)  ① 粘了原文 → 只切原话（chunk_user_jd）
                            ② 没粘、岗位在目录里 → external_sources.build_official_evidence
                               护栏：每技能≤2 条、全局≤24 条、required 优先、缺 source_id/原句即丢
                            ③ 两者皆无 → no_source 空证据 + 原因
                                ↓ job_evidence + retrieval_status + diagnostics
                        [2] Job Agent → job_requirements（+ 每条的 evidence_refs / level_basis / importance_basis）
                        [3] Assessment Agent → 能力差距（缺口带 gap_source_hint：这条要求的来路）
                        [4] Growth Agent
                        [5] Learning Agent ┐ 模型推断的要求进提示词时标注来路，
                        [6] Project  Agent ┘ 保留但不当地基（降权不删除）
                        [7] Plan Agent
                                ↓
              compute_jd_match（确定性汇总，非 Agent）→ 分母只数可判定要求；百分比由前端按 requirement_basis 决定
                                ↓
              backend/analyze.py: build_source_report(state) → 响应里的 source_report
                                ↓
              前端：EvidencePanel 按 provenance 分组（E 编号钉在数组下标，分组不重排）
                    EvidenceProvenanceCard 读四档计数 / 出处清单 / 陌生岗位四情形
```

## 5. 前端说明

- **只读后端结论**：所有来源判断都来自 `source_report`。前端不重算计数、不按技能名配对（`citations` 与
  `job_requirements` 逐条同序，按下标配对）、不在两处各判一遍 —— 否则必然漂成两个真相。
- **枚举中文只有一个出处**：`web/src/utils/enums.js` 的 `SOURCE_TYPE` / `REQUIREMENT_BASIS` / `RETRIEVAL_STATUS` /
  `EVIDENCE_STATUS` / `LEVEL_ORIGIN`。视图里不写死中文。
- **能回查 ≠ 这家公司的话**：摘要分组标题直接写「内置资料摘要（不是你粘贴的原文）」，
  摘要-only 那一轮明确写「所以不给"满足这份 JD"的匹配度」。
- **不给假百分比**：`knowledge_base` / `model_only` 两档下匹配度卡显示「这次给不出匹配度」+ 怎么补救，
  不摆一排 0。
- **TasksView 的快照说明按状态走**：`N 条依据（用内置资料摘要）`，0 条时显示「没有可回查的依据」。
- **降级不撒谎**：老结果缺 `source_report` 时如实说明；`StatusView` 在旧后端不返回 `knowledge.jobs` 时
  不参与健康判定（返回了就必须 ok）。
